# 設計: LTK 出場者配信状況サイト

要件: [requirements.md](requirements.md)

## アーキテクチャ

静的サイトを GitHub Pages で公開し、GitHub Actions の定期実行で配信状態を取得してサイトを再デプロイする。サーバーとデータベースは持たない。配信状態は毎回すべて取得し直し、前回の結果は保存しない。

GitHub Actions と Pages を無料で使うため、リポジトリは公開する。公開に伴う対策は次のとおり。

- Secret scanning と Push protection を有効にする
- トークンや API のレスポンス全体をログに出さない
- ワークフローの起動条件に `pull_request_target` を使わない
- 外部の Action は公式のもの（`actions/*`）だけを使う
- コミットには GitHub の noreply アドレスを使う
- YouTube の API キーは YouTube Data API 専用に制限する

```
┌──────────────────────── GitHub Actions（5分ごと / push / 手動）─────────────────────────┐
│                                                                                       │
│  data/*.yaml ──▶ ① 検証 ──▶ ② 配信状態の取得 ──▶ ③ site-data.json 生成 ──▶ ④ ビルド ──▶ ⑤ デプロイ │
│                   │          ├ Twitch Helix API                                     │      │
│                   │          └ YouTube RSS + Data API                               │      │
│                   └ 失敗したら中断（前回のサイトが残る）                                    │      │
└──────────────────────────────────────────────────────────────────────────────┼──────┘
                                                                               ▼
                                                     GitHub Pages（index.html, JS, site-data.json）
                                                                               ▲
                                                                       視聴者のブラウザ
```

- 秘密情報（Twitch のクライアントシークレット、YouTube の API キー）は GitHub Actions の Secrets に置き、取得処理の中だけで使う。配信されるファイルには含めない（AC-26）
- 取得結果はリポジトリにコミットせず、Pages のアーティファクトとして直接デプロイする。5 分ごとのコミットで履歴が膨らむのを避けるため
- LTK タグの判定は取得処理の中で行い、結果を site-data.json に書き込む。キーワードの変更は次の更新から反映される（AC-14）
- ブラウザは site-data.json を読み込んで画面を描画し、並び替えと絞り込みはブラウザ内で行う

### 構成の改訂（2026-10-26）

運用 1 日目に次の 3 つの課題が出たため、構成を改める。以下の内容は、この節より前の記述より優先する。

| 課題 | 原因 | 対応 |
|---|---|---|
| GitHub Actions の schedule が約 21 時間で 6 回しか動かない | GitHub 側で大きく間引かれる（設定は正常） | Cloudflare Workers の Cron Triggers から 5 分ごとに `workflow_dispatch` で起動する |
| YouTube の RSS が 8:35〜15:07（日本時間）にほぼ全チャンネルで 404 | YouTube 側が GitHub Actions の IP からの RSS を一時的に拒否していると見られる | RSS に失敗したチャンネルだけ YouTube Data API で取り直す（AC-40） |
| 公開 URL に GitHub のユーザー名を出したくない | `yas0090.github.io` | Cloudflare Pages（`*.pages.dev`）で公開し、GitHub Pages は停止する（AC-41） |

```
Cloudflare Workers（cron: */5 * * * *）
   └─▶ GitHub API: POST /repos/{owner}/{repo}/actions/workflows/deploy.yml/dispatches
          └─▶ GitHub Actions: 検証 → 取得（RSS 失敗分は API）→ ビルド → 秘密情報チェック
                 └─▶ wrangler pages deploy で Cloudflare Pages にアップロード（公開）
```

- **取得処理は GitHub Actions に残す**: Cloudflare Workers の無料プランは、1 回の実行で外部へのリクエストが 50 件まで、CPU 時間が 10ms までに制限される。今回の取得は約 70 件のリクエストがあり、1 回では収まらない。分割すると仕組みが複雑になるため、Workers は起動だけに使う
- **起動用の Worker**（`cron/` ディレクトリ）: `scheduled` ハンドラーで GitHub API の `workflow_dispatch` を 1 回呼ぶだけの小さな Worker。GitHub のトークンは Worker の Secret（`GITHUB_TOKEN`）に置く。トークンは fine-grained で、このリポジトリの Actions（読み書き）だけに権限を絞る。呼び出しに失敗したら Worker のログに残す。Cron で起動するだけなので、`workers.dev` の公開 URL は作らない（`workers_dev = false`）
- **GitHub Actions の schedule**: Worker が止まったときの予備として、1 時間ごと（`17 * * * *`）に減らして残す。実行が重なっても `concurrency` で 1 つずつ処理される
- **公開**: ビルドした `dist/` を `wrangler pages deploy` で Cloudflare Pages にアップロードする。Cloudflare の API トークン（Pages の編集だけ）とアカウント ID を GitHub の Secrets（`CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`）に置く。`wrangler` は devDependencies に入れてバージョンを固定する。Pages のプロジェクト名は `ltk4-livenow-unofficial` で、公開 URL は `https://ltk4-livenow-unofficial.pages.dev/`（URL だけで非公式と分かるようにする。2026-10-26 決定）。プロジェクトは初回だけ手元の wrangler で作り、ワークフローはアップロードだけを行う。wrangler 4.152 では Pages が Workers に統合され、`pages project create` は Workers 用の自動設定に置き換わるため、従来の Pages で作るように `--force` を付けた（一度作れば、以降の `pages deploy` は Pages に直接アップロードされる）
- **GitHub Pages の停止**: Cloudflare Pages で公開できたことを確認してから、リポジトリの設定で GitHub Pages を無効にする。ワークフローから Pages へのデプロイ（`upload-pages-artifact`, `deploy-pages`）も削除する
- **YouTube の取り直し**（AC-40）: RSS に失敗したチャンネルは、アップロード再生リスト（チャンネル ID の先頭 `UC` を `UU` に変えた ID）を `playlistItems.list`（`part=contentDetails`, `maxResults=10`、1 回 1 ユニット）で取得し、7 日以内の動画を候補にする。そのあとは RSS と同じく `videos.list` で配信中を判定する。API でも失敗したチャンネルだけ `error` にする
  - クォータ: RSS が全滅した回は 58 ユニット増える。前日の障害（約 6.5 時間）なら 1 日の合計は約 7,000 ユニットで、上限 10,000 に収まる。障害が丸 1 日続くと上限を超え、その日の残りは YouTube だけ「取得失敗」になる（太平洋時間 0 時に回復）
  - 実データでの確認（2026-10-26）: 配信中だった 12 チャンネルすべてで、配信中の動画がアップロード再生リストの先頭に載っていた

### データ取得の流れ（2026-10-26 整理）

1 回の実行で行う取得を、順番とリクエスト先ごとに整理する。Twitch と YouTube は並行して取得する。

```
Twitch                                         YouTube
① トークン取得（1）                             ④ RSS（チャンネルごと、10 件ずつ並行、無料）
② /helix/streams（100 人ずつ）                  ⑤ ④ に失敗したチャンネルだけ playlistItems.list（1 件 1 ユニット、AC-40）
   → 配信中・タイトル・サムネイル                ⑥ videos.list（候補 50 件ずつ、1 回 1 ユニット）
③ /helix/users（100 人ずつ）→ アイコン画像         → 配信中・タイトル・サムネイル
                                                ⑦ channels.list（50 件ずつ、1 回 1 ユニット）→ アイコン画像
                     ↓
          LTK 判定 → site-data.json に出力
```

| 手順 | 取得する情報 | リクエスト数（出場者 60 人、YouTube 58 チャンネル） | YouTube クォータ |
|---|---|---|---|
| ①〜③ | Twitch の配信状態・サムネイル・アイコン | 3 | − |
| ④ | YouTube の候補の動画 ID | 58 | 0 |
| ⑤ | ④ に失敗したチャンネルの候補 | 0〜58 | 0〜58 |
| ⑥ | YouTube の配信状態・サムネイル | 約 6 | 約 6 |
| ⑦ | YouTube のアイコン | 2 | 2 |
| 合計 | | 約 70〜128 | 約 8〜66（5 分ごとで 1 日約 2,300〜19,000） |

- 配信のサムネイル（AC-42）は ② と ⑥ の応答に含まれるので、追加のリクエストはいらない
  - Twitch: `thumbnail_url` のテンプレート `{width}x{height}` を `440x248` に置き換える
  - YouTube: `snippet.thumbnails.medium`（320×180、16:9）を使う
- 1 日のクォータが上限を超えるのは、RSS がほぼ丸 1 日失敗し続けた場合だけ。そのときは YouTube だけ「取得失敗」になる

### YouTube のクォータ管理（AC-21, AC-43、2026-10-26 追加）

この節の内容は「データ取得の流れ」の YouTube 部分より優先する。

**1 回の実行（5 分ごと）で行うこと**

| 処理 | 頻度 | YouTube クォータ |
|---|---|---|
| Twitch の配信状態（開始も終了も 1 回でわかる） | 毎回 | − |
| YouTube の終了チェック: 前回配信中だった動画 ID を `videos.list` で確かめる | 毎回 | 1（50 本まで） |
| YouTube の新しい配信の確認: 配信中でないチャンネルの RSS → 失敗分は `playlistItems.list` → 候補を `videos.list` | 下の間隔で | 約 7（RSS 正常時）〜約 55（RSS 全滅時） |
| アイコン画像: Twitch の users、YouTube の `channels.list` | 1 時間に 1 回（それ以外は前回の URL を使う） | 2 |

- **節約 A**: 前回配信中だった YouTube のチャンネルは、新しい配信の確認の対象から外す（終了チェックだけ）。配信が終わったら次の回から対象に戻す。同じチャンネルで同時に 2 本目の配信を始めた場合は、1 本目が終わるまで気づけない（許容する）
- **節約 B**: アイコン画像は 1 時間に 1 回だけ取り直す

**新しい配信の確認の間隔**

- 夜（日本時間 16:00〜翌 3:00）: 常に 5 分ごと。クォータは太平洋時間 0 時（日本時間 16 時、夏時間中は 17 時）にリセットされるので、夜は予算に余裕がある
- 朝・昼（日本時間 3:00〜16:00）: その日（太平洋時間）の使用量に応じて変える

  | 使用量 | 間隔 | 取り直し（RSS 失敗時の `playlistItems.list`） |
  |---|---|---|
  | 〜5,000 | 5 分 | 5 分に 1 回まで |
  | 5,000〜7,000 | 10 分 | 10 分に 1 回まで |
  | 7,000〜8,000 | 15 分 | 15 分に 1 回まで |
  | 8,000〜9,000 | 30 分 | しない |
  | 9,000〜、または API が `quotaExceeded` を返した | 止める | しない |

- 段階の区切りと間隔は `data/youtube-budget.yaml` に書き、取得処理の最初に検証して読み込む。運用しながら、Google Cloud Console の実際の使用量と見比べて調整する
- 間隔の判定は、前回の確認時刻からの経過時間で行う。cron の遅れを吸収するため、間隔から 1 分を引いた時間が経っていれば確認する

**使用量の数え方と、前回の結果の引き継ぎ**

- YouTube API の残りクォータを返す API はないため、取得処理が呼んだ回数から使用量を数える
- 取得処理は、公開サイトの `state.json` を最初に読み込み、最後に新しい `state.json` を `site-data.json` と一緒に公開する。中身は次のとおり（秘密情報は含めない）

  ```ts
  type FetchState = {
    version: 1;
    quota: { day: string; used: number; exceeded: boolean }; // day は太平洋時間の日付
    lastDiscoveryAt?: string;   // 最後に新しい配信の確認をした時刻
    lastFallbackAt?: string;    // 最後に取り直しをした時刻
    avatarsFetchedAt?: string;  // 最後にアイコン画像を取り直した時刻
    youtubeLive: Record<string, string[]>; // 配信中のチャンネル ID → 動画 ID
    youtubeErrors: string[];               // 前回の確認で失敗したチャンネル（確認しない回は「取得失敗」を引き継ぐ）
    avatars: Record<string, string>;       // チャンネルのキー → アイコン画像の URL
  };
  ```

- `quota.day` が今の太平洋時間の日付と違えば、使用量を 0 に戻す
- デプロイに失敗した回の使用量は記録に残らず、数えた値は実際より少なくなりうる。そのため上限は 10,000 ではなく 9,000 として扱い、`quotaExceeded` の応答を確実な合図として止める
- `state.json` を読み込めない場合（初回、サイトの障害など）は、使用量 0・前回の配信なし・アイコン画像なしとして、すべて取得する
- 公開サイトの URL は、GitHub Actions の変数（`PUBLIC_SITE_URL`）で渡す

**実データでの確認（2026-10-26、夜）**: 1 回目は新しい配信の確認とアイコン画像の取得で 9 ユニット（videos.list 7 + channels.list 2）。直後の 2 回目は確認の間隔内なので終了チェックだけになり 1 ユニット。配信中の 12 チャンネルはそのまま配信中と判定され、アイコン画像は前回の URL を使い回した

**見積もり（1 日）**

| 状況 | 動き | 使用量 |
|---|---|---|
| RSS が正常な日 | 1 日中 5 分ごと（公開後の実績の最大は 4,589） | 約 2,400 |
| RSS が 6.5 時間失敗 | 障害中は使用量が増え、5,000 を超えると自動で 10 分、15 分…と間隔が広がる（朝・昼の概算。夜は 5 分のまま） | 約 6,000〜7,000 |
| RSS が丸 1 日失敗 | 段階的に間隔が広がり、9,000 で止まる | 9,000 以内 |

### 配信のサムネイル（AC-42、2026-10-26 追加）

- **データ**: `Stream` に `thumbnailUrl` を加える
- **選手カード**: カードの上部に 16:9 の画像枠を常に確保し、その下に今の 3 行（名前・アイコン・タイトル）を置く。配信の有無にかかわらず、カードの大きさは変わらない
  - 配信中: 最初の配信のサムネイルを表示し、配信ページへのリンクにする
  - 配信していない: 薄いチームカラーの枠の中央に「OFFLINE」と表示する。アイコン画像は名前の横にあるので、枠には置かない（2026-10-26 変更）
  - 配信中でサムネイルがない、または読み込めない: 「LIVE」と表示する（OFFLINE と出すと LIVE バッジと食い違うため。2026-10-26 変更）
- **キャッシュ**: Twitch のサムネイルは URL が同じまま数分おきに中身が更新されるので、取得処理で URL に取得時刻を付けて、古い画像がブラウザに残らないようにする
- **大きさ**: PC の選手カードは約 100px から約 220px の高さになる。スマートフォン（2 列）では画像枠の幅は約 150px になる

## 技術選定

| 対象 | 採用 | 理由 |
|---|---|---|
| ホスティング | GitHub Pages | 公開リポジトリなら無料。データファイルや定期実行と同じ場所で管理できる |
| 定期実行 | GitHub Actions（schedule） | 公開リポジトリなら実行時間が無制限で無料。Secrets で秘密情報を管理できる |
| 言語 | TypeScript（Node.js 24） | 取得処理と画面で、型と判定ロジック（正規化、並び順）を共有できる |
| 画面 | Vite + TypeScript（フレームワークなし） | 画面は一覧と絞り込みだけで小さい。依存を減らして保守を軽くする |
| データファイル | YAML | 手で編集しやすく、コメントを書ける |
| データ検証 | zod | スキーマから型も作れ、エラー内容がわかりやすい |
| テスト | Vitest | Vite と設定を共有できる |

### 検討して採用しなかった案

- **Cloudflare Workers（Cron Triggers + KV、または訪問時に取得してキャッシュ）**: 定期実行の時刻は GitHub Actions より正確。ただし無料プランでは、外部へのリクエストが 1 回の実行につき 50 件までに制限される。YouTube の RSS はチャンネルごとに 1 件かかるので、出場者 60 人の多くが YouTube を使うと上限を超える。CPU 時間（1 回 10ms）も、RSS の解析で上限に近づくおそれがある
- **AWS Lambda + EventBridge + S3**: 支払いの上限を止める仕組みがなく、公開した取得先に大量アクセスが来ると請求が発生しうる（AC-24 に反する）
- **ブラウザから直接 API を呼ぶ**: Twitch のアプリトークンの発行にはクライアントシークレットが必要で、ブラウザには置けない。YouTube は訪問のたびにクォータを消費し、すぐに上限に達する
- **YouTube の `search.list`（eventType=live）**: 1 回 100 ユニットかかり、無料枠（1 日 10,000 ユニット）では 1 日 100 回しか呼べない（AC-25 を満たせない）
- **YouTube のチャンネル `/live` ページの解析**: 公式の API ではなく、ページの構造が変わると動かなくなる

## データモデル

### 入力: `data/teams.yaml`（管理者が編集する）

```yaml
teams:                      # 書いた順がチームの表示順（AC-2）
  - id: team-a              # 英数字とハイフン。絞り込みの識別に使う
    name: チームA
    color: "#EF6400"        # チームカラー（LTK 公式サイトの CORE の色、AC-28）
    players:                # 書く順は自由（表示は階級・ロールで並び替える）
      - name: 選手1
        tier: Next          # Next | Core | Masters
        role: TOP           # TOP | JG | MID | ADC | SUP
        channels:           # 1 つ以上
          - platform: twitch
            login: example_login
          - platform: youtube
            channelId: UCxxxxxxxxxxxxxxxxxxxxxx
```

### 入力: `data/keywords.yaml`

```yaml
ltkKeywords:
  - LTK
```

### 検証ルール（AC-23）

- 必須項目: チームの `id`・`name`・`color`（`#RRGGBB` 形式）、選手の `name`・`tier`・`role`、1 つ以上の `channels`
- `tier` と `role` は上の列挙値だけを許す
- `twitch` は `login`（英数字とアンダースコアで 25 文字以内）、`youtube` は `channelId`（`UC` で始まる 24 文字）を必須にする
- 定義にないキーはエラーにする（書き間違いが無視されるのを防ぐ）
- 1 チームの中で、同じ `tier` と `role` の組み合わせが重複したらエラーにする
- チーム `id` の重複と、同じチャンネルの重複登録はエラーにする。Twitch の `login` は Twitch 側と同じく大文字・小文字を区別せずに比べる
- 検証に失敗したら処理を終了コード 1 で終える。デプロイは行われず、前回のサイトが残る。GitHub からワークフロー失敗の通知メールが届く

### 出力: `site-data.json`（取得処理が生成し、ブラウザが読み込む）

```ts
type SiteData = {
  generatedAt: string;          // ISO 8601。最終更新日時（AC-9, AC-10）
  teams: {
    id: string;
    name: string;
    color: string;              // チームカラー（AC-28）
    players: {
      name: string;
      tier: "Next" | "Core" | "Masters";
      role: "TOP" | "JG" | "MID" | "ADC" | "SUP";
      avatarUrl?: string;       // チャンネルのアイコン画像。取得できなければ省略（AC-27）
      channels: {
        platform: "twitch" | "youtube";
        channelUrl: string;     // チャンネルページ（AC-6）
        state: "live" | "offline" | "error";   // error = 取得失敗（AC-22）
        streams: {              // state=live のときだけ要素がある。複数同時配信に対応（AC-8）
          title: string;
          url: string;          // 配信ページへの直接リンク（AC-7）
          ltk: boolean;         // LTK タグ（AC-12, AC-13）
        }[];
      }[];
    }[];
  }[];
};
```

- チームの並び順はデータファイルの順のまま出力する。階級とロールの並び替えは画面側で行う
- 選手が配信中かどうかは「どれかのチャンネルが live」で判定し、画面側で計算する

## 配信状態の取得

### Twitch

1. Client Credentials Flow でアプリのアクセストークンを取得する（`TWITCH_CLIENT_ID`, `TWITCH_CLIENT_SECRET`）
2. `GET /helix/streams?user_login=...&type=live` を、100 件ずつ呼ぶ
3. 返ってきた login は `live`、返ってこなかった login は `offline` にする
4. リクエストが失敗した場合は、そのバッチに含まれる全チャンネルを `error` にする
5. Twitch の配信ページはチャンネルページと同じ URL（`https://www.twitch.tv/{login}`）になる

### YouTube

1. チャンネルごとに RSS（`https://www.youtube.com/feeds/videos.xml?channel_id=...`）を取得し、直近の動画 ID を集める。RSS はクォータを消費しない
   - 公開日時が 7 日以内の動画だけを候補にして、API の呼び出し回数を減らす。公開日時は `published` と `updated` の新しい方を使う（事前に枠を作った配信は `published` が古いまま配信が始まり、候補から漏れていたため。2026-10-27 修正）
   - RSS の取得に失敗したチャンネルは `error` にする
2. 候補の ID を `videos.list`（`part=snippet,contentDetails`）で 50 件ずつ問い合わせる。1 回 1 ユニット（`YOUTUBE_API_KEY`）
3. 次の 2 つをどちらも満たす動画を配信中とみなす
   - `snippet.liveBroadcastContent == "live"`。これで配信予定（`upcoming`）は除外できる
   - `contentDetails.duration == "P0D"`。プレミア公開は動画の長さを持つので、これで除外できる
4. 配信中の動画が 1 本以上あれば `live`、なければ `offline` にする。`videos.list` が失敗した場合は、そのバッチに関係するチャンネルを `error` にする

**クォータの見積もり**: 出場者は 60 人（4 チーム × 15 人）。最も多い場合として全員が YouTube チャンネルを持ち、候補が平均 5 本と仮定すると、1 回の実行で 300 本＝6 ユニットかかる。288 回/日で 1,728 ユニット/日となり、上限 10,000 に対して十分な余裕がある（AC-25）。

**実データでの確認結果（2026-10-25）**

- 配信中の動画は `liveBroadcastContent=live` かつ `duration=P0D` だった。配信予定は `upcoming` で、正しく除外された
- 配信中の動画は RSS に載っていた。RSS の `published` は配信を始めた日時ではなく、配信枠を作った日時（配信開始の数分〜十数時間前）だった
- Twitch はログイン名の大文字・小文字に関係なく判定できた。存在しないログイン名は `offline` になる
- 存在しない YouTube チャンネルは RSS が HTTP 404 になり、`error` になる
- 出場者5人・6チャンネルの生成は約1秒で終わった

**残っているリスク**

- 進行中のプレミア公開は、確認時に実例が見つからず検証できていない。誤って配信中と判定されたとしても、表示が増えるだけで実害は小さい
- RSS には最新の 15 本しか載らない。何日も前に作った配信枠は、その後に 15 本以上の動画を投稿すると RSS から外れ、配信中でも検出できない。配信の直前に枠を作る、または枠を作らずに配信を始める通常の運用であれば問題にならない

### チャンネルのアイコン画像（AC-27）

- Twitch は `GET /helix/users?login=...`（100 件ずつ）の `profile_image_url`、YouTube は `channels.list`（`part=snippet`、50 件ずつ、1 回 1 ユニット）の `snippet.thumbnails` を使う

### LTK タグの判定（AC-12, AC-13）

```ts
const normalize = (s: string) => s.normalize("NFKC").toLowerCase();
const isLtk = (title: string, keywords: string[]) =>
  keywords.some((k) => normalize(title).includes(normalize(k)));
```

  - 現在時刻が「その日の 16:00（開始時刻が 16:00 より前の本戦は開始時刻）」以上、終了予定時刻未満
  - 現在時刻が同じ時刻以上で、公式チャンネルのどちらかが配信中（終了予定時刻を過ぎても続ける）

## 更新履歴（AC-56〜63、2026-10-31 追加）

## お気に入り選手（AC-64〜76、2026-10-31 追加、#23）

- 状態は `favorites: string[]`（`playerKey` の登録順）。`src/web/app.ts` が持ち、切り替えのたびに `saveFavorites` で保存する
- 純粋関数は `src/shared/favorites.ts`: `toggleFavorite`（なければ末尾に追加、あれば除く）、`pruneFavorites`（今のデータにいない選手と重複を除く。順序は保つ）、`favoritePlayers`（登録順に `{team, player, key}` を返す）
- 保存は `src/web/storage.ts` の `loadFavorites` / `saveFavorites`（キー `ltk-stream-status:favorites:v1`）。非表示の保存と同じく `readItem` / `writeItem` を使い、形式違い・例外は空配列。登録順を保つため並べ替えない。保存領域が使えなくても、メモリ上の `favorites` で動き続ける
- 星ボタンは `<button type="button" class="fav-btn" aria-pressed>`。ラベルは状態で変えず `<選手名> のお気に入り`。選手カードの名前の行の右端に置く。アイコンは `icons.ts` の `starIcon`（輪郭／塗りつぶし）
- お気に入り欄 `renderFavorites`（`render.ts`）は `<section class="favorites">` に見出しと登録順のカードを並べる。0 人なら作らない。各カードは `--team-color` をその選手のチームの色にした `.fav-item` に入れ、一覧と同じ `renderPlayerCard` を使う
- 欄は `data.teams` と `favorites` だけから作り、`filter` と `hiddenPlayers` を使わない（AC-70）。一覧は今までどおり `buildView` で作るので、お気に入りの選手も残る（AC-71）
- `favorites-slot` を `filters-slot` の前に置く（お知らせ・エラーの後）。切り替えで欄と一覧の両方を描き直し、5 分ごとの再読み込みでも両方を描き直す。フィルタ操作では欄に触れない
- 再読み込みのたびに `pruneFavorites` を通し、元と違うときだけ保存へ書き戻す（AC-76）
- 切り替えで DOM が作り直されるので、押した後は押したボタンと同じ側（欄か一覧）の同じ `playerKey` のボタンへフォーカスを戻す。欄で解除して欄から外れたときは、欄の同じ位置（末尾なら直前）のボタンへ戻し、欄が空になったら戻さない。画面が飛ばないよう `preventScroll` を付け、反対側へは移さない（2026-10-31 変更。押すたびに欄や一覧へスクロールしていた）
- 採用しなかった案: `Set` + `sort` で保存する（登録順が失われる）、欄を `buildView` の結果に混ぜる（絞り込みの影響を受ける）

## ヘルプ（AC-77〜89、2026-10-31 追加、#25）

- `src/web/help.ts` の `renderHelp(storage?)` が `{ button, dialog, autoOpen }` を返す。更新履歴（`changelog.ts`）と同じく `<dialog class="help">` を `showModal()` で開き、閉じるボタンは `dialog.close()`、Esc はブラウザ標準に任せる
- ボタンは `<button class="help-button" aria-label="ヘルプ">?</button>`。`app.ts` が最初に 1 回だけ作り、`header-meta` の更新履歴の枠の隣に置く。データに依存しないので再描画では作り直さない（AC-88）
- 保存は `storage.ts` の `HELP_SEEN_KEY`（`ltk-stream-status:help-seen:v1`）、`shouldAutoShowHelp`、`markHelpSeen`。`shouldAutoShowHelp` は試し書きと削除が通り、かつキーが未設定のときだけ true（読めても書けない環境で毎回出るのを防ぐ）。キーの `v1` は保存形式の版で、文章を変えても上げない
- 記録は `close` イベントで書く（閉じるボタンでも Esc でも発火。ボタンから開いた場合も同じ）。自動表示は `app.ts` が DOM 追加後に `autoOpen()` を呼ぶ
- 内容は `<h3>` 見出し 5 つ。アイコンは `starIcon`、`platformIcon`、`.live-badge` を使い、`aria-hidden` にして意味は隣の文章で伝える
- サンプルカード（AC-90）は `render.ts` の `renderPlayerCard` をそのまま使い、`help.ts` の固定の選手データから作る。サムネイルは SVG の data URI をコードに埋め込み、外部へ取りに行かない。カード全体に `inert` を付けてリンクを操作できなくし、お気に入りの `control` には空の登録と何もしない処理を渡し、星だけ見せる。カードは `.help-sample` の枠で囲む。見出し（AC-92）は背景の帯と左の太線で飾り、本文に `word-break: auto-phrase` と `line-break: strict` を指定して文節で改行する
- フィルタの説明文（AC-91）は `filters.ts` の見出し「絞り込み」・チップ名・「解除」・「詳細フィルタ」と同じ語を使う。`tests/web/help.test.ts` が語の有無を確かめる
- スタイルは `.changelog` と揃え、本文に `overflow-y: auto` を付けてモーダル内をスクロールさせ、狭い幅では余白を減らす

## ワークフロー（`.github/workflows/deploy.yml`）

- **起動条件**
  - `schedule: */5 * * * *`（AC-21）
  - `push`（main ブランチ）
  - `workflow_dispatch`
- **手順**: checkout → 依存のインストール → テスト → データ検証と取得（site-data.json 生成）→ Vite でビルド → 秘密情報の混入チェック → `actions/upload-pages-artifact` → `actions/deploy-pages`
  - テストはコードやデータが変わったとき（push、手動）だけ実行し、定期実行では省く
- **同時実行**: `concurrency: pages` を指定する。実行中のデプロイは途中で止めず、待機中の古い実行は新しい実行に置き換える
- **注意点**
  - 公開リポジトリでは、60 日間リポジトリに動きがないと定期実行が自動で止まる。大会期間中はデータの更新で動きが出る想定だが、運用メモに残す
  - カスタムワークフローでデプロイする場合、Pages のビルド回数の上限（1 時間 10 回）は適用されない
